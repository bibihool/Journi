# Journi — System Architecture & Technical Specifications

This document outlines the complete system architecture, component breakdown, design rationale, operational constraints, and future migration roadmap for **Journi**, an AI-powered travel planning web application.

## 2. Frontend Layer

The frontend interface is engineered using Next.js 16.3 with React 19, TypeScript 5.9, and Tailwind CSS v4. Interactive message components leverage `react-markdown` paired with `remark-gfm` for rendering markdown structures, while Lucide React provides modern iconography. Browser-native speech recognition is enabled via the Web Speech API.

Next.js 16 and React 19 were selected because they provide first-class streaming support using standard Web Streams, instant hydration, and a clean split between server components and interactive client components such as the chat input, sidebar drawer, and modal windows. Tailwind CSS v4 provides a zero-runtime CSS engine with modern CSS variable theming, allowing Journi to default to a sleek dark charcoal aesthetic while allowing users to switch to a clean light mode seamlessly. The combination of `react-markdown` and `remark-gfm` ensures that complex multi-day itineraries, formatted tables, bold attractions, and bullet lists generated by the AI render beautifully. The Web Speech API was chosen to give travelers a convenient, hands-free voice input option without introducing third-party audio service costs.

Regarding constraints, streaming token-by-token text produces frequent component re-render cycles in React. This is mitigated by isolating streaming state to the active message component and debouncing scroll calculations. Additionally, the Web Speech API depends on native browser support; it functions smoothly across Chrome, Edge, and Safari, but is not natively supported in Mozilla Firefox, where the UI gracefully displays a helpful fallback notice.

## 3. Backend Layer

The backend is built using Next.js App Router Route Handlers executing on the Node.js 22 serverless runtime. Real-time streaming between the backend and the browser is delivered using Server-Sent Events over standard `ReadableStream` interfaces.

This architecture was chosen to establish a unified fullstack repository where API endpoints and UI views live together, sharing identical TypeScript types and schemas without requiring a separate Express or Python server. Server-Sent Events allow incoming token chunks from the AI to be streamed to the client immediately, reducing Time-to-First-Token to under half a second. Proxying requests through serverless route handlers also guarantees that sensitive API credentials remain completely hidden from the client browser.

In terms of constraints, Vercel enforces a serverless execution timeout of fifteen to sixty seconds on the Hobby tier. For lengthy multi-day itineraries generated by slower models, there is a risk of function termination if the stream takes too long. This is mitigated by selecting high-throughput models like Nemotron 3.5 Lightning, which generates over eighty tokens per second. Furthermore, because serverless functions are stateless, the backend does not hold in-memory conversation state between HTTP calls, meaning every conversation and message must be persisted to the database.

## 4. Database & Persistence Layer

The persistence layer uses an embedded SQLite database driven by Prisma ORM 7.10 via the `@prisma/adapter-better-sqlite3` driver adapter. In the local development environment, the database lives in the repository root, while in the Vercel serverless environment, an initialized template database is copied into the writable temporary filesystem directory.

SQLite and Prisma 7 were chosen because they provide zero-infrastructure data storage with no external database servers to manage, no connection pooling services to configure, and zero hosting costs. Prisma 7 introduces strict compile-time TypeScript validation for conversation, message, and saved trip models, while allowing schema synchronization via automated migration commands. To solve the challenge of Vercel serverless containers having read-only root directories, Journi includes a pre-seeded template database that is copied into the writable temporary folder on first execution, giving the application immediate read and write access without external database setup.

The main constraint is serverless ephemerality. Because serverless temporary storage is tied to individual container instances, local database records reset when a container is recycled or scaled down after prolonged inactivity. Additionally, SQLite uses file-level write locks, which makes it less suited for heavy concurrent write traffic.

## 5. External APIs & Third-Party Services

Journi integrates the OpenRouter API for conversational AI completions, OpenStreetMap for location preview embeds, and GitHub for version control and automated continuous deployment.

OpenRouter was selected because it aggregates state-of-the-art free-tier open models, such as NVIDIA Nemotron 3.5 Lightning with a one-million token context window, Nex N2.5 Pro, and Google Gemma 4 31B, under a unified, OpenAI-compatible streaming API without requiring individual vendor accounts. OpenStreetMap provides a completely free, open-source mapping iframe solution that requires no API keys, credit cards, or billing quota monitoring. GitHub serves as the central code repository, triggering automated production builds whenever changes land on the main branch.

The primary constraint with OpenRouter free-tier models is strict rate limiting, generally around twenty requests per minute and fifty to two hundred requests per day, along with occasional model availability rotations. Journi mitigates this by catching rate-limit errors and presenting friendly user-facing messages, alongside an in-app model selector that lets users switch to another active free model instantly.

## 6. Hosting & Deployment Infrastructure

The application is hosted on Vercel's Global Edge Network and Serverless Compute platform, deployed live at `https://journi-umber.vercel.app`, and connected to the GitHub repository at `https://github.com/bibihool/Journi`.

Vercel was chosen as the premier hosting environment for Next.js applications, offering automatic code splitting, optimized static asset caching for brand icons and fonts, automatic SSL certificate provisioning, and global edge routing. The direct GitHub integration enables automated continuous integration and continuous deployment, ensuring that every commit pushed to the main branch is compiled, verified, and deployed with zero downtime.

The key constraint encountered on Vercel was the read-only serverless filesystem, which initially conflicted with SQLite file creation. This was resolved by declaring native SQLite dependencies in Next.js configuration and dynamically routing database operations to the temporary writable filesystem.

## 7. Future Tech Stack Roadmap & Considerations

As Journi evolves beyond its initial architecture, several targeted upgrades to the technology stack are planned to unlock advanced features and support higher user volume:

First, we plan to transition the mapping layer from OpenStreetMap iframe embeds to the **Google Maps Platform API**. While OpenStreetMap is excellent for lightweight static destination views, migrating to Google Maps will unlock critical travel planning features such as the **Google Maps Directions & Routes API for multi-stop itinerary route optimization**, interactive turn-by-turn navigation between daily attractions, real-time public transit schedules, estimated walking and driving times between itinerary checkpoints, Google Street View previews, and rich Places API metadata including user ratings, opening hours, and photos.

Second, we anticipate migrating the persistence layer from local ephemeral SQLite to a managed distributed cloud database such as **Turso** or **Neon PostgreSQL**. Turso uses libSQL and offers a direct serverless SQLite-compatible architecture, allowing seamless migration while providing permanent data persistence across all Vercel serverless regions. Alternatively, moving to Neon or Supabase PostgreSQL will enable user authentication, multi-device cloud synchronization of saved itineraries, and shared trip collaboration between multiple travelers.

Third, the AI integration layer will be significantly enhanced by implementing native AI function calling and tool use. This will transform Joojoo from a conversational generator into an active, autonomous travel assistant capable of executing specialized external tools directly within the conversation. Specifically, we will implement real-time flight searching tools (connecting to APIs such as Amadeus or Skyscanner) to look up live airfares, flight schedules, layovers, and airline seat availability, alongside live lookup tools that fetch up-to-date travel information including current weather forecasts, currency exchange rates, visa entry requirements, destination safety advisories, and seasonal local event schedules. Additionally, the system will support hybrid model routing, allowing travelers to stay on free OpenRouter tiers for standard planning or toggle high-tier models (such as Claude 3.7 Sonnet or GPT-4o) when handling ultra-complex multi-country logistics, automated booking confirmations, and rich PDF itinerary generation.
